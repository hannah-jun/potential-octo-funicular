# 저녁 메뉴 선택 + 장보기 체크리스트

## 사용자에게 보이는 결과

- 사용자는 로그인 없이 사이트에 접속해 바로 카테고리를 선택할 수 있다.
- 레시피 이름으로 검색해 537개 목록을 바로 좁힐 수 있다.
- 음식 종류(한식/서양/퓨전/중국/일본/이탈리아/동남아시아, 7종)와 조리 방식(밥/국/찌개·전골·스튜/볶음/구이 등, 21종) 두 축으로 필터링해 레시피 목록을 좁힐 수 있다.
- 목록의 각 레시피는 조리 방식에 맞는 이모지와 음식 종류별 색상으로 구분되어, 텍스트만 있을 때보다 한눈에 훑어볼 수 있다.
- 필터링된 레시피 목록에서 하나를 클릭하면 해당 레시피의 재료 목록을 볼 수 있다.
- 재료 목록의 각 항목에 체크박스가 있어 이미 집에 있는 재료를 체크할 수 있다.
- 체크하지 않은 재료만 모은 장보기 목록이 실시간으로 표시된다.
- 재료 목록 아래에 조리 순서(순번, 설명, 있으면 과정 팁)가 순서대로 표시된다.

## 승인된 범위

- 카테고리 필터(2축) → 레시피 목록 → 레시피 상세(재료 체크, 조리 순서) → 장보기 체크리스트로 이어지는 흐름 전체.
- 레시피 데이터는 정식 서비스키로 인증하는 공공 오픈API에서 사전에 수집해 로컬에 저장해둔 데이터셋(레시피 537건)만 사용한다.
- 로그인, 계정, 사용자의 레시피 등록 없이 누구나 바로 쓸 수 있는 보기 전용 사이트.

## 관찰 가능한 인수 기준

- 음식 종류와 조리 방식을 각각 하나씩 선택하면, 두 조건을 모두 만족하는 레시피만 목록에 나타난다.
- 검색어를 입력하면 레시피 이름에 그 글자가 포함된 레시피만 남고, 카테고리 필터와 동시에(AND로) 적용된다.
- 조건에 맞는 레시피가 하나도 없으면, 목록 대신 안내 메시지가 표시된다.
- 레시피 상세 페이지에 들어가면 브라우저 탭 제목이 그 레시피 이름으로 바뀐다.
- 레시피를 클릭하면 그 레시피의 재료 목록(원본 레시피의 재료명·수량 표기 그대로)이 표시된다.
- 재료 항목의 체크박스를 체크하면 그 재료는 장보기 목록에서 즉시 사라지고, 체크를 해제하면 다시 나타난다.
- 체크박스를 하나도 누르지 않은 상태에서는 장보기 목록에 재료 전체가 나타난다.
- 레시피 상세에는 조리 순서가 원본 데이터의 순번대로 나열되고, 해당 단계에 팁이 있으면 설명과 함께 표시된다.

## 확정된 제약과 근거

- 카테고리는 음식 종류 × 조리 방식 두 축 조합이다 — 뭘 먹고 싶은지 모를 때 선택지를 단계적으로 좁혀갈 수 있도록 하기 위함 (사용자 확인).
- 카테고리 값은 데이터가 실제로 제공하는 값(음식 종류 7종 × 조리 방식 21종)을 그대로 쓰고, 임의로 재분류하지 않는다 — 데이터 손실·억지 매핑 없이 정확한 값을 쓰기로 함 (사용자 확인).
- 레시피 선택은 목록에서 사용자가 직접 클릭하는 방식이다 — 무작위 추천보다 직접 훑어보고 고르는 방식을 선호함 (사용자 확인).
- 재료 보유 여부는 체크박스로 표시하고 부족한 재료만 남긴다 — 이번 스펙의 핵심 기능으로 사용자가 직접 요청함 (사용자 확인).
- 레시피 출처는 정식 서비스키로 인증하는 공공 오픈API다 — `PRODUCT.md`에서 확정된 경계.
- 로그인/계정 기능 없음 — `PRODUCT.md`에서 확정된 경계.

## 가정

- 재료 항목은 원본 레시피의 표기(이름 + 수량)를 그대로 보여주며, 체크 여부는 이름 기준으로만 판단하고 수량 자체는 비교하지 않는다.
- 원본 데이터의 재료 구분("주재료"/"부재료"/"양념")을 그대로 유지해서 보여준다.
- 체크박스 상태는 해당 레시피를 보는 동안에만 유지되며, 다른 레시피로 이동하거나 세션이 끝나면 초기화된다 (계정이 없어 별도 저장을 하지 않음).
- 음식 종류·조리 방식 각 축은 한 번에 하나씩만 선택할 수 있고, 두 축은 동시에(AND 조건으로) 적용된다.
- 재료 목록을 추출할 수 없었던 레시피(수집 실패 등)는 데이터셋에서 제외한다.
- 조리 순서 단계에 팁이 없으면 그 단계는 설명만 보여주고 팁 영역은 표시하지 않는다.

## 범위 밖 영역과 이유

- 재료별 쇼핑몰(쿠팡/컬리 등) 검색 링크 자동 생성 — `PRODUCT.md`에서 이후 확장으로 명시적으로 분리됨.
- 여러 레시피의 재료를 자동으로 합산하는 기능 — 같은 이유로 이번 범위에서 제외.
- 장보기 체크리스트를 파일로 내보내기/저장하는 기능 — 같은 이유로 이번 범위에서 제외.
- 사용자 계정, 로그인, 레시피 등록/즐겨찾기 — `PRODUCT.md`에서 보기 전용 사이트로 확정된 경계.
- 이 공공 오픈API 외 다른 레시피 출처(크롤링 포함) 사용 — `PRODUCT.md`에서 단일 출처로 확정.

## 보류된 사항

- API에서 데이터를 언제, 얼마나 자주 다시 수집할지는 이번 스펙에서 다루지 않는다. 초기 데이터셋을 한 번 사전에 수집해 사용하는 것으로 충분하다.
- 카테고리 조합별로 확보해야 할 최소 레시피 개수는 정하지 않았다.

## 남은 위험

- 실제 데이터가 한식에 크게 치우쳐 있어(537건 중 385건), 나머지 음식 종류 × 조리 방식 조합 상당수가 비어 있다. 조합에 따라 선택지를 좁혀가는 핵심 경험이 답답하게 느껴질 수 있다.
- API 서비스키가 만료되거나 정책이 바뀌면 `bun run fetch-recipes`로 데이터셋을 다시 만들 수 없게 될 수 있다.
- `PRODUCT.md`에 성공 신호가 아직 정해지지 않아, 이 스펙이 실제로 문제를 해결했는지 판단할 기준이 없다.
